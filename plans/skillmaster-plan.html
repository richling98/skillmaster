01 Problem & Solution

Why this project exists

🧩

Fragmented skills libraries

Claude Code stores skills in ~/.claude/skills/. Codex stores them in ~/.agents/skills/. There is no native way to share between them. Build a skill in one tool, manually duplicate it in the other — forever.

🔄

No single source of truth

Skills drift apart over time. Update one in Claude Code and forget to update Codex. No history, no rollback, no backup. Your "brain" is scattered across directories you probably don't think about.

⚙️

Manual sync is error-prone

Running copy commands after every skill change is friction that accumulates. It breaks the creative flow of building workflows and means sync often doesn't happen at all.

✅

SkillMaster solves all of this

One master folder. Automatic bidirectional sync. Create a skill anywhere — it appears everywhere. Your skills stay private, local, git-tracked, and portable across machines.

04 How the Watcher Works

A technical deep-dive — and an honest assessment of whether it will actually hold up

Layer 1 — Reliable polling service

The installed watcher uses a small polling loop by default. Every pass records the visible skill folders and SKILL.md checksums for the master, Claude Code, and Codex directories, then syncs the first meaningful create, edit, or deletion it detects. This avoids macOS privacy failures from event APIs following protected paths.

🍎

macOS — FSEvents API

Apple's native kernel-level API. Used by Time Machine, Spotlight, Xcode, and most sync tools on the Mac. When any file under a watched path changes, the kernel pushes an event immediately — no scanning, no delay. fswatch wraps this API in a simple CLI.

🐧

Linux — inotify API

Linux's equivalent kernel subsystem. inotifywait (from the inotify-tools package) wraps it the same way. Same behavior: events are pushed from the kernel the moment a write completes, with near-zero latency.

Layer 2 — optional foreground file events

For manual foreground debugging, scripts/watch.sh can still use fswatch on macOS or inotifywait on Linux when those tools are installed. The permanent launchd/systemd service runs in polling mode so normal setup does not require either dependency. 

# What the core watcher command looks like
fswatch -r \
    "$MASTER_DIR" \
    "$HOME/.claude/skills" \
    "$HOME/.agents/skills" | while IFS= read -r changed_path; do
    handle_event "$changed_path"
done

The -r flag makes it recursive (watches subdirectories). The watcher does not follow symlinks because Claude Code's skills directory contains many symlinks into larger tool trees, and following those can trigger macOS privacy errors. The pipe feeds each changed path into a bash handler function.

Layer 3 — The event handler logic

When a path arrives from fswatch, the handler does five things in sequence:

1

Identify which directory the change came from

Compare the changed path against the three watched directories to determine the source. Then extract the skill name (the immediate subfolder under the skills directory) and validate that the change is inside a SKILL.md file or a skill subfolder — not a temp file, a lock file, or an editor swap file (e.g. .swp, ~). 

skill_name=$(echo "$changed_path" | sed "s|$source_dir/||" | cut -d'/' -f1)
# Ignore non-skill paths (editor temp files, dot files, etc.)
[[ "$skill_name" == .* ]] && continue
[[ ! -f "$source_dir/$skill_name/SKILL.md" ]] && continue
2

Check if this event was caused by us (loop prevention)

This is the hardest part. When the watcher copies a file to a destination, that copy itself triggers a new fswatch event — which would trigger another copy — creating an infinite loop. We prevent this using MD5 checksum comparison: 

src_hash=$(md5sum "$source_dir/$skill_name/SKILL.md" | awk '{print $1}')
dst_hash=$(md5sum "$dest_dir/$skill_name/SKILL.md" 2>/dev/null | awk '{print $1}')

# If source and destination are already identical, do nothing.
# This is what breaks the loop: after we copy, the next event
# sees matching checksums and exits immediately.
[ "$src_hash" = "$dst_hash" ] && continue

This is more reliable than file-tagging approaches (like xattr) because many editors and tools strip extended attributes when saving. Checksums are pure file content — nothing can strip them.

3

Debounce — wait for the file to settle

Editors like VS Code often write a file in multiple rapid steps (write temp → rename → flush). Without debouncing, the watcher would fire 3-4 times for a single save. We add a short settle wait: 

sleep 0.5  # wait 500ms for the file to stop changing
# Re-read the hash after settling — if it changed during the wait,
# a new event will be coming anyway, so we can exit this one.
new_hash=$(md5sum "$source_dir/$skill_name/SKILL.md" | awk '{print $1}')
[ "$src_hash" != "$new_hash" ] && continue

500ms is imperceptible to a human but long enough to outlast virtually all editor save sequences.

4

Copy to destinations

Copy the skill folder to each destination that isn't the source and doesn't already have an identical copy. Log each operation to ~/.skillmaster/sync.log. 

for dest in "$MASTER_DIR" "$HOME/.claude/skills" "$HOME/.agents/skills"; do
  [ "$dest" = "$source_dir" ] && continue  # skip the source
  dest_hash=$(md5sum "$dest/$skill_name/SKILL.md" 2>/dev/null | awk '{print $1}')
  if [ "$src_hash" != "$dest_hash" ]; then
    cp -r "$source_dir/$skill_name/" "$dest/$skill_name/"
    echo "[$(date)] Synced $skill_name from $source_dir → $dest" >> ~/.skillmaster/sync.log
  fi
done
5

Regenerate the local sharing webpage

If the event changed the master folder, rebuild $MASTER_DIR/index.html from the current list of skill directories. The generated page is ignored by sync detection so it does not create another sync loop. 

if master_folder_changed "$changed_path"; then
  scripts/generate-index.sh "$MASTER_DIR"
  echo "[$(date)] Regenerated skill index page" >> ~/.skillmaster/sync.log
fi

Layer 4 — Persistence via launchd / systemd

The watcher is a long-running background process. Left to its own devices it would die when you close Terminal or restart your Mac. install-watcher.sh solves this by registering it as a system service:

🍎

macOS — launchd

A .plist file is written to ~/Library/LaunchAgents/ with KeepAlive = true. macOS loads it on login and automatically restarts the watcher if it ever crashes. This is exactly how tools like Dropbox and 1Password run in the background.

🐧

Linux — systemd user service

A .service file is installed to ~/.config/systemd/user/ with Restart=always. Enabled with systemctl --user enable skillmaster. Survives reboots automatically.

Edge cases and how they're handled

Edge caseRiskMitigation
Sync loop Copy triggers event triggers copy → infinite loop MD5 checksum comparison before every copy. After sync, source and dest are identical → next event exits immediately
Editor multi-step saves 3–4 events fire for one save operation 500ms debounce. Events within the settle window are absorbed; only the final state is synced
Symlinks in ~/.claude/skills/ Watcher follows symlink into gstack/ and hits protected or irrelevant nested paths Do not pass -L to fswatch. Real skill directories are watched recursively; symlinked tool trees are left alone.
System/built-in skills Bootstrap or watcher copies skill-creator, docx, etc. into master Configurable exclusion list in skillmaster.conf. Listed skill names are never synced or bootstrapped.
Skill deleted from Claude or Codex Auto-deletion propagates to master and causes data loss Deletions from tool directories are never auto-propagated. Only logged. Deletion only flows outward from master (with confirmation prompt).
Two skills edited simultaneously Race condition — two sync operations run at once fswatch pipes events sequentially through a single while read loop. Events queue and are processed one at a time — no concurrency risk in shell.
Generated index.html changes Regenerated sharing page triggers the watcher again Explicitly ignore $MASTER_DIR/index.html in sync detection. It is a generated artifact, not a skill.
fswatch not installed Watcher can't start setup.sh detects absence and installs via brew install fswatch (macOS) or apt install inotify-tools (Linux) before proceeding
Watcher crashes Sync stops silently launchd / systemd KeepAlive / Restart=always restarts the process automatically. Last restart time is visible in sync.log.

Honest verdict — will this actually work?

✅ What will definitely work
The core sync mechanism is sound. fswatch + FSEvents is used by professional sync tools in production. Checksum comparison is a well-established loop-prevention technique. The sequential event queue in bash eliminates concurrency risk. launchd persistence is battle-tested on macOS. For the primary use case — creating or editing a skill in one place and having it appear in the others — this will work reliably.
⚠️ What needs careful implementation
The sync loop prevention relies on the checksum check running before the copy. If the script has a bug that skips this check, a loop will occur. This must be rigorously tested. The debounce window (500ms) is a heuristic — very slow network drives or heavily loaded machines might need a longer settle time. The exclusion list for system skills must be accurate and kept up to date as Claude Code and Codex ship new built-in skills.
❌ What won't be handled (out of scope)
Merging conflicting edits (e.g. you edit the same skill in Claude Code and Codex simultaneously before sync fires) — the last-write wins. For skills files this is acceptable since they're small and rarely edited concurrently. Multi-machine sync (two Macs sharing one skills brain) is not covered — that would require git pull/push or a cloud folder, which is intentionally out of scope to keep skills private and local.

06 Scripts

What each component does

bootstrap.sh
NEW
Imports all existing skills into the master folder. Run once during setup.
  • Scans ~/.claude/skills/ and ~/.agents/skills/ for every skill (any folder containing a SKILL.md)
  • Copies each one into the master folder
  • On conflict (same skill name, different content): shows a diff and prompts the user to choose which version to keep
  • Skips system-bundled skills that shouldn't be in the master repo (configurable exclusion list)
  • Produces a summary: how many skills imported, how many conflicts resolved
watch.sh
NEW
The heart of SkillMaster — bidirectional auto-sync. Runs continuously in the background.
  • Watches all three directories simultaneously: master folder, ~/.claude/skills/, and ~/.agents/skills/
  • Installed services use polling mode for reliability; foreground debugging can use fswatch or inotifywait when present
  • On any file creation or modification, determines the source and propagates to the other two
  • Debounces rapid changes (e.g. editor saving multiple times) so it only syncs once per edit
  • Logs all sync events to ~/.skillmaster/sync.log for debugging
  • Skips sync loops by comparing checksums before copying
  • Runs generate-index.sh after master-folder changes so the local skill sharing page stays current
generate-index.sh
NEW
Builds the local skill sharing webpage.
  • Scans the master folder for every skill directory containing SKILL.md
  • Extracts each skill's name, description, updated time, and raw markdown content
  • Writes $MASTER_DIR/index.html as a static page that opens directly in the browser
  • Provides a readable skill preview and a Copy button for each skill
  • Escapes skill content safely before embedding it in the generated HTML
  • Can be run manually, but is normally called by watch.sh after any master-folder change
install-watcher.sh
NEW
Makes the watcher permanent — runs automatically on login.
  • On macOS: installs a launchd plist to ~/Library/LaunchAgents/, starts it immediately
  • On Linux: installs a systemd --user service, enables and starts it
  • Copies runtime scripts into ~/.skillmaster/runtime/scripts/ and runs the service in polling mode
  • After install, the watcher survives reboots with no manual intervention
sync.sh
UPDATED
Manual push from master → Claude Code + Codex. Useful when the watcher is off or for CI/scripting.
  • sync.sh — sync all skills
  • sync.sh email-digest — sync a single skill by name
  • sync.sh --dry-run — preview what would be synced without making changes
setup.sh
NEW
One-command install for any new user.
  • Asks: where should the master skills folder live? (default: ~/skills)
  • Writes a config file at ~/.skillmaster/config
  • Runs bootstrap.sh to import existing skills
  • Runs generate-index.sh so the master folder immediately contains a browsable index.html
  • Copies the bundled add-new-skill meta-skill into Claude Code + Codex
  • Runs install-watcher.sh to start auto-sync
  • Prints a summary of what was set up
add-new-skill
SKILL
The meta-skill — creates and deploys a new skill from inside any AI tool.
  • Guides Claude/Codex through capturing the skill's name, description, and instructions
  • Writes the SKILL.md to the master folder
  • The watcher automatically picks it up and propagates to both tools
  • Falls back to running sync.sh manually if the watcher isn't running
  • Updates the master README.md skills index

08 Design Decisions

Key questions answered

Q: Where does the master folder live?
User-configurable. During setup.sh, the user specifies any path they want. The choice is saved to ~/.skillmaster/config and used by all scripts and the watcher automatically.
Q: Are personal skills committed to the GitHub repo?
No. The GitHub repo contains only tooling (scripts, watcher, meta-skills). The user's master skills folder is entirely local and private. They can optionally push their skills to a separate private GitHub repo for backup and multi-machine sync — but this is never required.
Q: What happens when a skill is deleted from Claude Code or Codex?
It is NOT auto-deleted from the master folder. Deletion is only propagated outward from master → tools (with a confirmation prompt), never inward. This prevents accidental data loss.
Q: What about system/built-in skills that ship with Claude Code or Codex?
Excluded by default. A configurable list of skill names to skip during bootstrap and sync (e.g. skill-creator, gstack variants). Users can customize this list.
Q: How is the sync loop problem avoided?
Checksum comparison + debouncing. Before copying, the watcher compares source and destination checksums. If they already match, the event is ignored. A 500ms debounce prevents multi-fire from editors saving incrementally.
Q: How does the local HTML sharing page stay up to date?
Generated after master-folder changes. generate-index.sh rebuilds $MASTER_DIR/index.html during setup and after every successful sync into the master folder. The watcher ignores the generated HTML file itself so the rebuild does not trigger another sync cycle.
Q: Does copying a skill send it anywhere?
No. The page uses the browser clipboard only. It copies raw SKILL.md text locally so the user can paste it into Teams, email, docs, another AI tool, or any other surface they choose.
